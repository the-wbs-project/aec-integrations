# `apps/api/scripts/`

Maintenance / ops scripts run from a developer machine (or CI) against the app
database. **Not deployed to the Worker.** The app database is **Cloudflare D1**
(SQLite) + Drizzle (ADR 0016); a plain Node process reaches a *deployed* D1 only
through `wrangler d1 execute --remote`, not a Worker `env.DB` binding. None of
these use Prisma or a Postgres `DATABASE_URL`/`DIRECT_URL` — that path was retired
with the D1 migration (ADR 0016 / AECI-278).

| Script | npm script | What it does |
|---|---|---|
| `seed-reviews.ts` | `db:seed-reviews` | **Dev/demo only.** Inserts ~150–200 realistic, anonymous, approved reviews across the existing catalog so an operator can preview a "fully going" site (rating summaries, the 5-review threshold, pagination). The deterministic plan + SQL lives in `@aeci/shared/seed-reviews` (so `apps/datatool` can reuse it against a D1 binding); this is the Node CLI shell (arg parsing + `wrangler d1 execute` I/O). Not wired into `db:seed:local` on purpose. |
| `reconcile-product-counts.ts` | `db:reconcile-counts` | Denormalized product-count drift guard. Recomputes `integration_count` / `review_count` / `rating_*_avg` from source rows and compares to stored values. The rule lives in `src/lib/recompute-counts.ts`; this is the CLI/CI caller. Scheduled daily, report-only, against staging + production by `.github/workflows/reconcile-counts.yml`. |
| `reconcile-algolia-drift.ts` | `db:reconcile-algolia-drift` | Algolia index-drift report + orphan sweep for a deployed D1 (AECI-266). Builds the authoritative promoted-id sets from D1, browses each Algolia index, and (with `--apply`) deletes objects with no promoted D1 row. The rule lives in `src/lib/algolia-orphans.ts`. Dry-run by default. |
| `purge-algolia-orphans.ts` | `ops:purge-algolia-orphans` | One-off ops CLI (AECI-267) that deletes specific orphaned Algolia objects **by objectID** from an env's indexes. Core: `src/lib/algolia-orphan-purge.ts`. Dry-run by default; `--apply` deletes. |
| `retract-product.ts` | `ops:retract-product` | Remove a promoted product from a deployed D1 (there is no product-delete path in the app — `promote` only upserts). The usual case is a duplicate/stub that disambiguated to a `-N` slug (`box` existed → the dupe became `box-2`). Reads the product's full footprint, then on `--apply` deletes it child→parent (FK-safe regardless of D1 cascade), NULLs its `page_views` rather than deleting them (including either pair side since AECI-929, so the other endpoint keeps the view), de-indexes the Algolia `products` object, and purges the affected Cache-Tags. Core: `src/lib/retract-product.ts`, whose `PRODUCT_FK_HANDLING` gives every FK into `products` an explicit outcome (`retract-product-fk-coverage.spec.ts` fails on a new one). Dry-run by default; **refuses** a product with integrations, reviews or product versions unless `--force`; **refuses** a product that is the connector or an endpoint of any connector-evidenced pair unless `--delete-evidenced-pairs`, which `--force` does **not** imply (AECI-904). The footprint prints those pairs per role (as connector, as endpoint A, as endpoint B). The flag never covers a **vendor-held** pair (claimed, or `origin = 'vendor'`): that is a refusal, `--force` or not (AECI-1088). The delete plan re-checks both vendor-held refusals at write time: its first statement aborts the run if a vendor-held integration or pair entered scope after the footprint read, and the product DELETE carries the same guard. When that fires, the CLI prints that a vendor-held row entered scope since the dry run and nothing was written, and exits `1`. Re-run the dry run to see which row. An empty table-definition read for either table throws (could not check) rather than switching the refusal off. With the flag, their attestations, claims and the pairs themselves are deleted explicitly, child to parent, never by cascade, and each pair's `pair:{min}__{max}` tag plus `product:` for both endpoints and the connector join the purge set. Without it, the product DELETE is also guarded on no pair existing, so a pair that appeared after the check blocks the delete instead of cascading away; **always refuses** a connector catalogue or stub mapping, `--force` or not; refuses `production` unless `--allow-production`. Writes its §26.1 **tombstones** in the same batch (AECI-687): `product.deleted`, `integration.deleted` per deleted edge (`metadata.table` says which table), `integration.updated` per detached `powered_by`, `review.deleted`, `product_version.deleted`; actor `system`, `--operator <email>` recorded in metadata. |
| `backfill-entitlements.ts` | `ops:backfill-entitlements` | One-off §2.4 backfill for the AECI-515 entitlement model: inserts a perpetual, termless `active` `vendor_entitlements` row for every `vendors.verified = 1` with no row, restoring the §2.1 mirror invariant on a deployed tier (the fixture seeds never run remotely, so deployed tiers get their rows from here). Core: `src/lib/backfill-entitlements.ts`. **Never writes `vendors.verified`** — only `src/lib/vendor-entitlement.ts` moves the mirror, so reverse drift (an `active` entitlement on a `verified = 0` vendor) is reported and **refused** rather than repaired. Dry-run by default; `--apply` writes; `production` needs `--allow-production`; idempotent (`WHERE NOT EXISTS` re-guard). Writes **no** `audit_log` row (Tier-0; `notes` carries the provenance). Run it on **every** deployed tier — the `entitlement_mirror_drift` data-quality check is the proof it landed. |
| `backfill-licenses.ts` | `ops:backfill-licenses` | One-off E1.5 back-fill for the license model (AECI-1354, `VENDOR_SIGNUP_PROCESS.md` §5 E1, `STAGE_2_PAID_TIERS_SPEC.md` §2.4). For every vendor with a `vendor_admin` seat or a `vendor_entitlements` row that carries no license yet, writes the missing billing account (name = company name) and the licenses that mirror its entitlement row, mapped by `licenseTermsForEntitlement` (the rule the E1.4 dual-write uses): `active` → one live license per owned product, at least one (unassigned with no products); `expired` / `revoked` → the same set already ended (`end_reason` `lapsed` / `revoked`), keeping their products as history; `pending` → none. One `billing_account.backfilled` audit row per vendor (actor `system`, `--operator` in metadata), in the same `wrangler d1 execute` as that vendor's inserts. Core: `src/lib/backfill-licenses.ts`. The report lists perpetual rows (no `period_end`: `complimentary`, `ends_at` NULL, need a date decision), zero-product vendors, and mirror drift. **Never writes `vendors.verified`**: a vendor in `entitlement_mirror_drift` either way is refused and listed, and the exit code is `1` while any is. Dry-run by default; `--apply` writes; `production` needs `--allow-production`; refuses a tier without migration 0073. Idempotent: vendors with a license are skipped, ids are UUIDv5, every INSERT is `WHERE NOT EXISTS`-guarded, so a re-run writes nothing. Then, for **every** vendor (already licensed or not), a stamp reconcile copies the entitlement's `expiry_notice_sent_at` onto live licenses of the same term (`period_end` = `ends_at`, compared normalised) that lack it, so the AECI-1356 license sweep does not warn a term the old sweep already warned. It fills only a NULL stamp and names only `expiry_notice_sent_at` and `updated_at`. Each vendor stamped gets one `license.expiry_stamp_reconciled` audit row (actor `system`, `entity_type` `billing_account`, `metadata.license_ids`, `metadata.source` `ops:backfill-licenses`) in the same execute as its UPDATE. The audit INSERT runs first, guarded on the UPDATE's own WHERE, so it lands only when the UPDATE stamps something, and a re-run writes none. The dry run lists those licenses per vendor, with the audit-row count. After `--apply` it re-plans (nothing left), re-reads the stamp lag (none left) and re-reads the drift. Run it on **every** deployed tier before E1.6; the `license_mirror_drift` data-quality check is the proof it landed. **Cutover order:** back-fill, deploy E1.6/E1.7, then re-run the back-fill before the next 11:00 UTC expiry run, to copy any stamp the old sweep wrote in between. |
| `backfill-metrics-daily.ts` | `ops:backfill-metrics-daily` | Reconstruct the pre-snapshot segment of `metrics_daily` on a deployed (or local) D1 (AECI-581 / `ADMIN_PANEL_SPEC.md` §7.1). The 00:15 snapshot cron only knows the days it has run, so this fills the earlier ones from `page_views`, `audit_log`, and `products.created_at`. Writes **flow** metrics only — a past *total* is unrecoverable (§4), so stocks begin at the first cron run. Core: `src/lib/metrics-backfill.ts`. Dry-run by default; **refuses** a range containing unclassified page views (`is_bot IS NULL`) unless `--force`, because `metrics_daily` is kept indefinitely and would freeze the wrong human/bot split — run `scripts/ops/backfill-page-view-bots.sql` first. That gate is skipped on a run that selects no `traffic.*` series, since it protects the traffic split and such a run writes none. `--series <metric[,metric]>` narrows **both** passes to the named keys (AECI-684), which is the only way to extend one series' range: the zero-fill runs edge to edge, so a wider `--from` would stamp `traffic.*` = 0 across days `page_views` did not exist for. A catalog-only run also **refuses** (without `--force`) a range holding page views on days `metrics_daily` has no row for, because zero-filling them satisfies the §7.4 prune gate and the retention cron would then delete the raw rows their traffic series was never built from. Re-runnable: a `reconstructed` value can never overwrite a `measured` one. No `audit_log` row (ADR 0022). |
| `submit-trade-urls.ts` | `ops:submit-trade-urls` | Announce published `/trades/:slug` pages to IndexNow **outside a promote**. The ping normally rides the post-commit promote hooks, so retuning `TRADE_PUBLISH_MIN_PRODUCTS` (`TRADES_VOCABULARY.md` §6) changes which trade pages are indexable with nothing to announce them. Discovers candidates from `GET {site}/api/taxonomy`, then keeps only pages that actually return 200 **without** a `noindex` robots tag — it reads indexability off the deployed site rather than recomputing the floor, so it can't drift from the constant, can't ping a `noindex` URL, and doubles as proof the deploy + cache purge landed. Reuses the tested transport in `src/lib/indexnow.ts` — the one remaining caller that submits **directly** rather than through the AECI-826 buffer, because it runs from a laptop with no D1 access and announces a set the promote path never touches. Dry-run by default; `--apply` submits, `production` needs `--allow-production`, and it refuses to submit if the `{key}.txt` file doesn't resolve. No D1, no `audit_log` row. (AECI-747 removed the Google Indexing API submission — that API accepts only `JobPosting`/`BroadcastEvent`, so it never did anything for our pages.) |
| `traffic-classification-shadow.ts` | `ops:traffic-shadow` | Runs the AECI-872 traffic classifier in shadow over `--from`/`--to` (`ADMIN_PANEL_SPEC.md` §13 D19, `POST_LAUNCH_MONITORING.md` §3c). Pulls `page_views` and `asn_registry` read-only, loads them into an in-memory SQLite built from the real migrations, runs the existing detectors unchanged, and sets each row's new class beside today's digest verdict. Core: `src/lib/traffic-shadow.ts` and `src/lib/traffic-classifier.ts`. Every statement passes a SELECT-only guard. The default target is production by its Cloudflare name `aeci-app-production-us`, run from `/tmp` with `CLOUDFLARE_API_TOKEN` unset so wrangler uses the OAuth login; `--local` reads the local D1. Labels come from `.context/aeci-872/labels.json` (shape: `traffic-shadow-labels.example.json`). Reports go to `.context/aeci-872/`, which is gitignored. Writes nothing to any D1 and no `audit_log` row. |
| `generate-notifications-doc.ts` | `docs:notifications`, `docs:notifications:check` | Renders `docs/NOTIFICATIONS.md` from the notification registry (`src/lib/notifications/registry.ts`) plus the PostHog alert list (AECI-1200). Core: `src/lib/notifications/render-doc.ts`. `--check` renders to memory and exits `1` when the committed doc differs. Root `pnpm lint` runs the check, so it gates the required "Lint & typecheck" CI job. Run from the repo root as `pnpm docs:notifications`. No D1, no network. |

See each script's file header for its full flag set, required environment
variables (`CLOUDFLARE_API_TOKEN` for `--remote`; `ALGOLIA_APP_ID` /
`ALGOLIA_ADMIN_KEY` for the Algolia tools), and runbook.
