# `apps/api/scripts/`

Maintenance / ops scripts run from a developer machine (or CI) against the app
database. **Not deployed to the Worker.** The app database is **Cloudflare D1**
(SQLite) + Drizzle (ADR 0016); a plain Node process reaches a *deployed* D1 only
through `wrangler d1 execute --remote`, not a Worker `env.DB` binding. None of
these use Prisma or a Postgres `DATABASE_URL`/`DIRECT_URL` — that path was retired
with the D1 migration (ADR 0016 / AECI-278).

| Script | npm script | What it does |
|---|---|---|
| `seed-reviews.ts` | `db:seed-reviews` | **Dev/demo only.** Inserts ~150–200 realistic, anonymous, approved reviews across the existing catalog so an operator can preview a "fully going" site (rating summaries, the 5-review threshold, pagination). The deterministic plan + SQL lives in `@aeci/shared/seed-reviews` (so `apps/datatool` can reuse it against a D1 binding); this is the Node CLI shell (arg parsing + `wrangler d1 execute` I/O). Not wired into `db:seed:local` on purpose. |
| `reconcile-product-counts.ts` | `db:reconcile-counts` | Denormalized product-count drift guard. Recomputes `integration_count` / `review_count` / `rating_*_avg` from source rows and compares to stored values. The rule lives in `src/lib/recompute-counts.ts`; this is the CLI/CI caller. Scheduled daily, report-only, against staging + production by `.github/workflows/reconcile-counts.yml`. |
| `reconcile-algolia-drift.ts` | `db:reconcile-algolia-drift` | Algolia index-drift report + orphan sweep for a deployed D1 (AECI-266). Builds the authoritative promoted-id sets from D1, browses each Algolia index, and (with `--apply`) deletes objects with no promoted D1 row. The rule lives in `src/lib/algolia-orphans.ts`. Dry-run by default. |
| `purge-algolia-orphans.ts` | `ops:purge-algolia-orphans` | One-off ops CLI (AECI-267) that deletes specific orphaned Algolia objects **by objectID** from an env's indexes. Core: `src/lib/algolia-orphan-purge.ts`. Dry-run by default; `--apply` deletes. |
| `retract-product.ts` | `ops:retract-product` | Remove a promoted product from a deployed D1 (there is no product-delete path in the app — `promote` only upserts). The usual case is a duplicate/stub that disambiguated to a `-N` slug (`box` existed → the dupe became `box-2`). Reads the product's full footprint, then on `--apply` deletes it child→parent (FK-safe regardless of D1 cascade), NULLs its `page_views` rather than deleting them (including either pair side since AECI-929, so the other endpoint keeps the view), de-indexes the Algolia `products` object, and marks the sitemap dirty with `wrangler kv key put sitemap:dirty` (AECI-1945). The same batch stamps `vendors.updated_at` on every vendor whose products sit on a deleted or detached edge, with the database clock and never at or behind the stored `vendors` watermark, so the 08:00 Algolia sync rewrites their reach counts (AECI-2193). It then prints the steps it cannot do, in run order: the `POST /admin/purge` body for the affected Cache-Tags, the Algolia drift and count reconcilers, and on production the upstream `delete_product` + `confirm_retractions` (`src/lib/retract-followups.ts`, `docs/runbooks/catalog.md` "Retracting a product or vendor by hand"). Core: `src/lib/retract-product.ts`, whose `PRODUCT_FK_HANDLING` gives every FK into `products` an explicit outcome (`retract-product-fk-coverage.spec.ts` fails on a new one). Dry-run by default; **refuses** a product with integrations, reviews or product versions unless `--force`; **refuses** a product that is the connector or an endpoint of any connector-evidenced pair unless `--delete-evidenced-pairs`, which `--force` does **not** imply (AECI-904). The footprint prints those pairs per role (as connector, as endpoint A, as endpoint B). The flag never covers a **vendor-held** pair (claimed, or `origin = 'vendor'`): that is a refusal, `--force` or not (AECI-1088). **`--withdraw-connector`** (AECI-2047) is the one exception: it implies `--delete-evidenced-pairs`, lists every pair it would delete in the dry run, and deletes the vendor-held pairs the product delivers as connector that one of its own vendors holds, with their hold on each tombstone. Every other vendor-held row and a connector catalogue still refuse (`docs/runbooks/catalog.md` "Withdrawing a connector"). The delete plan re-checks both vendor-held refusals at write time: its first statement aborts the run if a vendor-held integration or pair entered scope after the footprint read, and the product DELETE carries the same guard. When that fires, the CLI prints that a vendor-held row entered scope since the dry run and nothing was written, and exits `1`. Re-run the dry run to see which row. An empty table-definition read for either table throws (could not check) rather than switching the refusal off. With the flag, their attestations, claims and the pairs themselves are deleted explicitly, child to parent, never by cascade, and each pair's `pair:{min}__{max}` tag plus `product:` for both endpoints and the connector join the purge set. Without it, the product DELETE is also guarded on no pair existing, so a pair that appeared after the check blocks the delete instead of cascading away; **always refuses** a connector catalogue or stub mapping, `--force` or not; refuses `production` unless `--allow-production`. Writes its §26.1 **tombstones** in the same batch (AECI-687): `product.deleted`, `integration.deleted` per deleted edge (`metadata.table` says which table), `integration.updated` per detached `powered_by`, `review.deleted`, `product_version.deleted`; actor `system`, `--operator <email>` recorded in metadata. |
| `retract-vendor.ts` | `ops:retract-vendor` | Remove a promoted vendor that owns nothing from a deployed D1 (AECI-1024 rule: zero products and zero owned edges in both `integrations` and `connector_evidenced_pairs`; profiles, seat invites and billing accounts refuse too). There is no `--force`, and one refusing vendor refuses the whole run. Dry-run by default; `--apply` needs `--confirm-count N` equal to the plan size, and `production` needs `--allow-production`. On `--apply`, per vendor in one batch: deletes its review replies and the field contests it filed, NULLs its `integration_field_challenges`, `page_views`, `claims` and `attestations` references, deletes the vendor, and writes one §26.1 `audit_log` row in the same batch (AECI-1226). It then de-indexes the Algolia `vendors` object and marks the sitemap dirty with `wrangler kv key put sitemap:dirty` (AECI-1945). It prints the steps it cannot do, in run order: the `POST /admin/purge` body for `vendor:<slug>`, the Algolia drift reconciler, and on production the upstream review-app cleanup (`src/lib/retract-followups.ts`, `docs/runbooks/catalog.md` "Retracting a product or vendor by hand"). Core: `src/lib/retract-vendor.ts`. |
| `backfill-metrics-daily.ts` | `ops:backfill-metrics-daily` | Reconstruct the pre-snapshot segment of `metrics_daily` on a deployed (or local) D1 (AECI-581 / `ADMIN_PANEL_SPEC.md` §7.1). The 00:15 snapshot cron only knows the days it has run, so this fills the earlier ones from `page_views`, `audit_log`, and `products.created_at`. Writes **flow** metrics only — a past *total* is unrecoverable (§4), so stocks begin at the first cron run. Core: `src/lib/metrics-backfill.ts`. Dry-run by default; **refuses** a range containing unclassified page views (`is_bot IS NULL`) unless `--force`, because `metrics_daily` is kept indefinitely and would freeze the wrong human/bot split — run `scripts/ops/backfill-page-view-bots.sql` first. That gate is skipped on a run that selects no `traffic.*` series, since it protects the traffic split and such a run writes none. `--series <metric[,metric]>` narrows **both** passes to the named keys (AECI-684), which is the only way to extend one series' range: the zero-fill runs edge to edge, so a wider `--from` would stamp `traffic.*` = 0 across days `page_views` did not exist for. A catalog-only run also **refuses** (without `--force`) a range holding page views on days `metrics_daily` has no row for, because zero-filling them satisfies the §7.4 prune gate and the retention cron would then delete the raw rows their traffic series was never built from. Re-runnable: a `reconstructed` value can never overwrite a `measured` one. No `audit_log` row (ADR 0022). |
| `submit-trade-urls.ts` | `ops:submit-trade-urls` | Announce published `/trades/:slug` pages to IndexNow **outside a promote**. The ping normally rides the post-commit promote hooks, so retuning `TRADE_PUBLISH_MIN_PRODUCTS` (`TRADES_VOCABULARY.md` §6) changes which trade pages are indexable with nothing to announce them. Discovers candidates from `GET {site}/api/taxonomy`, then keeps only pages that actually return 200 **without** a `noindex` robots tag — it reads indexability off the deployed site rather than recomputing the floor, so it can't drift from the constant, can't ping a `noindex` URL, and doubles as proof the deploy + cache purge landed. Reuses the tested transport in `src/lib/indexnow.ts` — the one remaining caller that submits **directly** rather than through the AECI-826 buffer, because it runs from a laptop with no D1 access and announces a set the promote path never touches. Dry-run by default; `--apply` submits, `production` needs `--allow-production`, and it refuses to submit if the `{key}.txt` file doesn't resolve. No D1, no `audit_log` row. (AECI-747 removed the Google Indexing API submission — that API accepts only `JobPosting`/`BroadcastEvent`, so it never did anything for our pages.) |
| `traffic-classification-shadow.ts` | `ops:traffic-shadow` | Runs the AECI-872 traffic classifier in shadow over `--from`/`--to` (`ADMIN_PANEL_SPEC.md` §13 D19, `POST_LAUNCH_MONITORING.md` §3c). Pulls `page_views` and `asn_registry` read-only, loads them into an in-memory SQLite built from the real migrations, runs the existing detectors unchanged, and sets each row's new class beside today's digest verdict. Core: `src/lib/traffic-shadow.ts` and `src/lib/traffic-classifier.ts`. Every statement passes a SELECT-only guard. The default target is production by its Cloudflare name `aeci-app-production-us`, run from `/tmp` with `CLOUDFLARE_API_TOKEN` unset so wrangler uses the OAuth login; `--local` reads the local D1. Labels come from `.context/aeci-872/labels.json` (shape: `traffic-shadow-labels.example.json`). `--capture-from` and `--exclude-ids` feed the AECI-1716 browser-report sections only (§3c). Reports go to `.context/aeci-872/`, which is gitignored. Writes nothing to any D1 and no `audit_log` row. |
| `identify-traffic-client.ts` | `ops:identify-traffic-client` | Names a client from its stored `user_agent_hash` and `cf_asn` (AECI-1580, `POST_LAUNCH_MONITORING.md` §3b). Lists the user agents Cloudflare saw on that network on one UTC day, hashes each one, marks the match, and reports what it fetched and how many IPs it used. Read-only, prints no IP, needs `CF_READONLY_API_TOKEN`. |
| `verify-acceptance-chain.ts` | `ops:verify-acceptance-chain` | Proves the agreement acceptance record was not edited (AECI-1680, ADR 0057). Read-only. It checks four things in order. First, that an R2 bucket lock rule covers `evidence/acceptance-chain/` in `aeci-uploads-<env>`: none is `LOCK MISSING`, a failure. Second, the chain itself, walked from R2 seq `000001` upward without trusting the D1 ledger: it reports the first broken link. Third, each file's DigiCert RFC 3161 token, with `openssl ts -verify` against the pinned `scripts/certs/digicert-tsa-chain.pem`, whose header names its source URLs. Fourth, every live `agreement_acceptances` and `license_grants` row against its last fingerprint in the chain: `CHANGED`, `UNEXPORTED`, `ABSENT` and `TOMBSTONE WITHOUT PRUNE AUDIT`. Core: `src/lib/acceptance-chain.ts`. `--env staging\|demo\|production`, or `--local` for the local D1 and R2 (no lock check). Exit `1` on any failure. Runbook: `docs/runbooks/legal.md`. |
| `generate-notifications-doc.ts` | `docs:notifications`, `docs:notifications:check` | Renders `docs/NOTIFICATIONS.md` from the notification registry (`src/lib/notifications/registry.ts`) plus the PostHog alert list (AECI-1200). Core: `src/lib/notifications/render-doc.ts`. `--check` renders to memory and exits `1` when the committed doc differs. Root `pnpm lint` runs the check, so it gates the required "Lint & typecheck" CI job. Run from the repo root as `pnpm docs:notifications`. No D1, no network. |

Retired (AECI-1358, 2026-10-17): `ops:backfill-entitlements` and `ops:backfill-licenses`.
Both were one-off back-fills that read `vendor_entitlements`. Both ran on every tier
before E1.6, and `license_mirror_drift` reads 0. Migration 0082 dropped the table, so the
scripts could not run again. Their source is in git history.

See each script's file header for its full flag set, required environment
variables (`CLOUDFLARE_API_TOKEN` for `--remote`; `ALGOLIA_APP_ID` /
`ALGOLIA_ADMIN_KEY` for the Algolia tools), and runbook.
