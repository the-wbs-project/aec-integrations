# Linear issue conventions

How an AECi Linear issue is written so that an agent can resolve what governs it. Two audiences:
whoever files the issue, and the `spec-anchor` skill that reads it.

**Why this file exists.** Linear's plan has no custom-field feature, so the spec anchor lives in the
issue description as a text convention. The templates that carry that convention live **only in
Linear** — there is no `.github/ISSUE_TEMPLATE/` here — so they drift with nothing in git to catch
it. Between 2026-05-13 and 2026-09-11 the Build template asked for `**Spec:**` while every consumer
looked for `**Spec section:**`, and nobody noticed for four months (AECI-601). This file is the
mirror that makes that drift reviewable.

`.agents/skills/spec-anchor/SKILL.md` is the consumer. If you change the grammar here, change its
step 1 in the same PR.

---

## 1. The `**Spec section:**` line

**First line of the description. Every issue. No exceptions.** It is the highest-signal input the
plan check has.

### The canonical forms

```
**Spec section:** §X.Y (docs/SPEC_NAME.md)
**Spec section:** §X.Y, §X.Z (docs/SPEC_NAME.md)
**Spec section:** §X.Y (docs/A.md); §P.Q (docs/B.md)
**Spec section:** docs/SPEC_NAME.md (whole document)
**Spec section:** n/a — <reason>. Governing docs: `docs/A.md` §X, `CLAUDE.md` §"Section title"
```

Real examples, all of which resolve:

```
**Spec section:** §5.4 (docs/ADMIN_PANEL_SPEC.md)
**Spec section:** §6.2, §6.4a (docs/STAGE_1_PHASE_6_SPEC.md)
**Spec section:** §4a (docs/CACHE_STRATEGY.md, cache key normalization / WC-4)
**Spec section:** §3 (docs/POST_LAUNCH_MONITORING.md); §13 (docs/ADMIN_PANEL_SPEC.md)
**Spec section:** n/a — process / tooling. Governing docs: `CLAUDE.md` §"Where to start"
```

### Rules

1. **Name the doc.** A bare `§9.3` with no doc means `docs/STAGE_1_SPEC.md`, which governs almost
   nothing now. If you mean another doc, say so — omitting it is how an anchor silently resolves to
   the wrong contract.
2. **Put the doc in parentheses after the sections, or lead with it.** Both parse. The parenthetical
   form is canonical because it reads better when one doc carries several sections.
3. **Separate sections with a comma, docs with a semicolon.** ` / ` and ` + ` also parse, because
   many existing issues use them. Prefer the canonical punctuation in new issues.
4. **A parenthetical may carry prose after the path** — `(docs/ADMIN_PANEL_SPEC.md, the visitor
   definition)` is fine and useful.
5. **`§` is optional but expected.** `§9.3` and `9.3` both parse. Keep a letter suffix attached —
   `§6.4a` is a different section from `§6.4`, and both exist.
6. **Free-text after the line is fine.** Cite an ADR, note a supersession, link a sibling issue.

### The `n/a` form

For work with no spec contract — tooling, process, a PostHog dashboard setting, an operator data
action, a live defect found incidentally.

```
**Spec section:** n/a — <one clause saying why>. Governing docs: `docs/A.md` §X, `CLAUDE.md` §"Title"
```

**Name at least one governing doc.** `n/a` alone drops the review to "constraints only", which
catches CRITICAL-tier violations and nothing else. A path outside `docs/` counts:
`.agents/skills/spec-anchor/`, `apps/api/src/lib/email.ts`, `DESIGN.md` at the repo root.

The skill accepts "Governing docs are", "Governing context", and "governed by" as equivalents — it
harvests any doc named on the line — but `Governing docs:` is the form to write.

### What does not parse

| Don't write | Why |
|---|---|
| `**Spec:** …` | The label is `**Spec section:**`. Nothing looks for `**Spec:**`. |
| `**Repo:** …` / `**Base branch:** …` instead of a spec line | Neither is an anchor. Add the spec line too; see §3 for repo routing. |
| `**Spec section:** the ADMIN_PANEL_SPEC` | Name the path, with the `.md`. |
| `**Base branch:** stage-2` | `stage-2` merged into `main` and was deleted on 2026-09-03 (ADR 0019). Everything branches from `main`. |

### Machine-authored issues are exempt

Claim and correction tickets are generated by `buildDescription()` in `apps/api/src/lib/linear.ts`
and carry a `Request: <uuid>` trailer instead. They are not build work and they do not need an
anchor. Don't hand-edit one to add a spec line.

## 2. Section numbers are load-bearing

Several spec docs say so explicitly: renumbering a section breaks every issue anchored to it. If you
must renumber, grep Linear for the old anchor first and update the issues in the same change.

## 3. Which repo, and how to route it

AECi spans three GitHub repos, and Linear issues for all three are filed on the **AECI** team. The
routing signal is the title prefix and the project, not the team. This mirrors `CLAUDE.md`
§"Sibling repos"; that table is the source of truth.

| Repo | Title prefix | Project |
|---|---|---|
| `aec-integrations` (the app) | none | the stage or epic |
| `aec-integrations-review` (curation upstream of promote) | **`REVIEW - `** | none |
| `aec-integrations-marketing` (all Markdown, no code) | none | **"Marketing"** |

This was AECI-601's open question 4 — *should review-app issues live on the AECi team at all?* —
and the answer is yes. One team, prefixed titles. Twenty-plus issues already follow it.

## 5. Measuring whether this is working

The check is not "does the line exist" — it is "does the line resolve". Those diverged badly once
and the first metric said everything was fine.

Sample the 20 most recently created issues, exclude machine-authored ones, and for each resolve the
line by hand against `spec-anchor` step 1. Count three outcomes separately:

1. resolves to the right doc and the heading exists,
2. resolves to a doc, but the heading is absent,
3. `n/a` with at least one governing doc named.

Anything else is a miss. The 2026-09-11 baseline (AECI-601) was 6 correct, 6 resolving to the
**wrong** doc, 2 partial, 5 `n/a` with no rung-1 hit, and 2 with no line at all.
