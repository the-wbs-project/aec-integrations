# Architecture Decision Records

Short, dated records explaining *why* specific decisions were made. Format: Context, Decision, Consequences.

See [adr.github.io](https://adr.github.io/) for the convention.

## Naming

`NNNN-short-decision-title.md` where NNNN is a four-digit sequential number starting at 0001.

- `0006-algolia-over-cloudflare-ai-search.md` — **Accepted**: Algolia + InstantSearch for search (ships Phase 3).

Resolved by retiring Prisma migrations entirely and adopting Supabase CLI migrations (`supabase/migrations/`). See `docs/migrations.md` for the current workflow.
- `0008-taxonomy-reference-data.md` — **Accepted**: the taxonomy vocabulary (categories/audiences/phases) is code-managed reference data, applied to every environment via idempotent upserts. After the D1 migration (ADR 0016, AECI-278) the seed file moved to `apps/api/seed/taxonomy.sql` and is applied to D1 via `wrangler d1 execute` (formerly Postgres `supabase/reference-data/taxonomy.sql` via `psql`). Supersedes the §13 "Airtable owns taxonomy" stance for the taxonomy facets only (vendors/products/integrations stay Airtable-owned).
- `0009-signal-forms.md` — **Accepted**: Angular v22 Signal Forms (`@angular/forms/signals`) is the standard for all new forms; forms reuse the shared `@aeci/shared` Zod schemas as the single source of validation truth, with `$localize` owning display copy. Documents the v22.0.0 `validateStandardSchema` + `validateHttp` incompatibility (NG0992) and the field-by-field workaround. Supersedes the "Reactive forms only" stance in `ANGULAR_STYLE_GUIDE.md` §13.
- `0010-promote-purges-cloudflare-directly.md` — **Accepted** (mechanism **reversed by ADR 0020**): `POST /api/promote` purges the edge cache by calling Cloudflare's purge-by-tag API directly (shared `@aeci/shared` transport), removing the api→web `WEB` service binding and the web↔api cycle from AECI-105. The SSR Worker's `POST /admin/purge` stays as the manual/CI surface. A Cloudflare Queue (Option C) is the deferred evolution if multiple cross-Worker purge producers or bulk-purge volume appear. **ADR 0020 adopts that Queue**: native Workers Cache makes the zone HTTP purge inert and `ctx.cache.purge()` entrypoint-scoped, so cross-Worker invalidation moves to a Cloudflare Queue consumed by the SSR Worker.
- `0010-angular-aria-alongside-spartan.md` — **Accepted** (2026-06-25, AECI-231; proposed 2026-06-05 from the AECI-129 spike, v22 epic AECI-122): adopt Angular Aria (`@angular/aria`, stable in v22) as the default for _new_ interactive/form-control patterns (select, combobox, listbox, radio, accordion, tree, grid, menu, toolbar, tabs) while **keeping Spartan** for the overlay primitives Aria lacks (Popover, Dialog) and migrating nothing reactively. Ratified once the review-submission form (AECI-200) landed as the reference Aria-in-forms implementation, alongside the Tabs pilot (AECI-132) and the header search combobox (AECI-144). Records two real-world deviations: (a) Aria@22 GA ships no `radio`/`select`, so listbox/combobox **stand in**; (b) discrete-choice Aria controls bridge into Signal Forms via `[(value)]`+`(valueChange)`, **not** `[formField]` (which works for native inputs only). Does not supersede ADR 0005 or 0009; informs but does not resolve the Spartan peer-override cleanup.
- `0011-canonical-uses-serving-origin.md` — **Accepted** (AECI-147): `<link rel="canonical">` and `og:url` use the **serving origin** (self-referential, multi-host), not a hardcoded apex — built once via `apps/web/src/app/core/canonical.ts` → `canonicalUrl()`. Future-proofs the pre-launch `demo.aecintegrations.com` → apex/www promotion; non-prod hosts are Access-gated so their self-canonicals never index. Sitemap/robots already used the serving origin, so they stay consistent for free; the 404 and `/preview/*` samples are documented exceptions. **Amended 2026-07-05:** the canonical served host flipped apex → `www.` (the SSR Worker now 301s the bare apex → `www.`); the self-referential mechanism is unchanged, only the fallback literals + `PUBLIC_SITE_URL` follow.
- `0012-browserstack-real-device-cross-browser.md` — status **Accepted** (2026-06-25; AECI-154): adopt **BrowserStack** (real-device cloud) as the cross-browser / real-device testing approach — a scope addition to `TESTING_STRATEGY.md` §7/§9 (which specs Playwright-multi-browser + Chromatic, no BrowserStack). MCP server wired for ad-hoc checks; the CI fan-out (existing Playwright suite → BrowserStack Automate, curated smoke subset, **real iOS Safari + real Android**) **shipped in Phase 7.8** as a **separate non-blocking** lane (`.github/workflows/browserstack.yml`), **inert until the personal-subscription `BROWSERSTACK_*` secrets are set**. Keeps the fast PR lane fast/free; reuses CF Access service-token headers for gated envs; **Percy not adopted** (Chromatic stays the visual tool).

- `0013-algolia-jobs-via-queue.md` — **Accepted** (2026-06-09): the two daily Algolia jobs (AECI-139 sync, AECI-140 drift) run as **cron → enqueue → consume**. The cron `scheduled()` handler only `queue.send()`s a typed message; a new `queue()` consumer on the same Worker runs the job (shared dispatcher, identical to an inline fallback used on local/preview where no queue is bound). Adds four queues (`aeci-algolia-{sync,drift}-{staging,production}`), provisioned by an idempotent `wrangler queues create` step before each API deploy. Narrows ADR 0010's "Queue deferred" note for the Algolia jobs only (promote-purge stays direct). PREREQS: Workers Paid plan + Queues-edit permission on the CI `CLOUDFLARE_API_TOKEN`.
- `0015-supabase-ssr-auth-on-workers.md` — **Accepted** (2026-06-10, AECI-193 / Phase 5.2): Supabase Auth on `workerd` lands as two permanent factories — `@supabase/ssr` cookie sessions on the SSR Worker (Hono `getAll`/`setAll` adapter) and **`jose`/JWKS** user-JWT verification on the private API Worker, **no DB round-trip and no `nodejs_compat`** (`AUTH_AND_RLS.md` §4). Spike outcomes recorded: `@supabase/ssr` runs clean on `workerd` (PKCE fallback not needed), issued tokens are **ES256** (HS256 fallback not needed), full cookie→session→bearer→JWKS chain proven. `SUPABASE_URL` is a public per-env var; `SUPABASE_ANON_KEY` is a web-Worker-only secret (graceful warn-and-skip now, **flips to REQUIRED in 5.5**); the service-role key never touches the web Worker (the API Worker later gained it per ADR 0016 §6 / AECI-530 for the Admin-API seams, unrelated to token verification). The `/auth/whoami` smoke routes are `THROWAWAY(AECI-193)`.
- `0014-instantsearch-js-over-angular-instantsearch.md` — **Accepted** (2026-06-10, AECI-142): build `/search` with **`instantsearch.js` + connectors → Angular signals** instead of the spec-named `angular-instantsearch`, which caps at `@angular/core <16`, is deprecated, and is NgModule/zone-based — unusable on this Angular 22 zoneless/SSR stack. SSR-safe via a dynamic `import()` isolated in a factory and run only inside `afterNextRender`; the SDK lands in a lazy `/search` chunk, never the initial/SSR bundle. Narrows `STAGE_1_SPEC.md` §7.5 (a forward-pointer edit is proposed); companion to ADR 0006. Records the deferred per-tab sort dropdown (needs Algolia replicas — AECI-175) and the `util` `externalDependencies` build note.
- `0016-d1-over-supabase-postgres.md` — status **Accepted** (2026-06-22; proposed 2026-06-13): migrated the application database from Supabase Postgres (Prisma Accelerate) to **Cloudflare D1** via **Drizzle**, **keeping Supabase for Auth only** (Option A — fewest moving parts, auth-only Supabase fits the free tier). The API Worker runtime is Drizzle/D1 only; remaining work is cloud D1 provisioning + secret pruning (Phase 5) and the landing-Postgres cut-over. Delivers edge read latency + partial cost reduction; **defers the single-vendor driver** and accepts a permanent split-identity seam (provisioning, `auth.users` reads, GDPR erasure become cross-system) plus the loss of RLS as defense-in-depth. Interacts with 0002 (Accelerate retired for the DB path), 0015 (Supabase Auth **retained**), 0007 (Supabase CLI migrations superseded by drizzle-kit + `wrangler d1`), 0013, 0010, 0008. Gated by Phase 0 spikes; **shelved**, not ratified, if a spike blocks. Records Option B (self-host auth, full Cloudflare consolidation) as the deferred end-state.
- `0017-single-supabase-auth-project-across-environments.md` — **Accepted** (2026-06-25): consolidate auth for **all environments** (local/preview/staging/production) onto **one dedicated Supabase project** (`ktuhnlypztujpsseujzx`), and move per-environment isolation from Supabase-project separation to **Cloudflare Access** (staging + preview gated as before; **production also gated until launch**, then opened). Resolves the per-project `auth.users.id` divergence that left an admin a stranger across environments (prod `profiles` empty/unestablishable). Auth is `SUPABASE_URL`-driven, so this is mostly config: flip `SUPABASE_URL` in both `wrangler.jsonc`s, the CSP ref, and `.dev.vars.example`; point both `SUPABASE_ANON_KEY_*` secrets + the per-env `SUPABASE_SERVICE_ROLE_KEY` at the new project; allow the `aeci-gh-actions` service token on the prod Access policy and plumb `CF_ACCESS_*` into the prod smoke. Accepts a **shared `auth.users`** (test-user pollution; the real authz boundary stays per-env D1 `profiles.role`) and removes the `refresh-staging.yml` auth dump/scrub/seed (it would truncate the now-shared users). The legacy Supabase-Postgres "public schema" CI gate is a **separate concern** on the old projects (AECI-256/257), untouched here. Retains ADR 0015 unchanged; builds on 0016 (service-role seams) and reuses 0012's Access service-token-in-CI pattern.
- `0019-main-is-production-line-stage-2-integration-branch.md` — **Accepted** (2026-07-05): production went live, so **`main` becomes the production/stable line** and **Stage 2 develops on a long-lived `stage-2` integration branch**. A deliberate, time-boxed exception to §10's "no long-lived branches" rule (this ADR **scoped-supersedes** `docs/CICD_PLAN.md` §10 for the Stage 2 window). Rationale: the promote chain is a single linear trunk gated by SHA, so once Stage 2 lands on `main` a hotfix SHA drags in every in-progress Stage 2 commit **and** `promote-to-prod`'s forward-only `wrangler d1 migrations apply` ships any Stage 2 schema to prod on the next promote — feature flags hide UI, not migrations (ADR 0016). Keeping `main` clean makes the existing hotfix path (branch→PR→merge→promote-by-SHA) work unchanged and guarantees prod D1 never sees a Stage 2 migration until `stage-2 → main` merges. No CI/CD change (staging still auto-tracks `main`; promote buttons already take an arbitrary SHA; `drift-check.yml` is base-branch-agnostic). Costs: long-lived-branch drift + an eventual large merge (mitigated by frequent `main → stage-2` merges) and migration-journal reconciliation before merge-up. Interacts with ADR 0016 (forward-only D1 migrations — the decisive constraint), 0017 (shared auth — unaffected).
- `0020-workers-cache-and-queue-purge.md` — **Accepted** (2026-07-12; AECI-314 / WC-1, AECI-315): migrate the hand-rolled edge cache (`caches.default` match/put in `server-runtime.ts` + the HTTP `callCloudflarePurge` purge) to **native Cloudflare Workers Cache** (`cache.enabled` in `wrangler.jsonc`; a HIT skips the Worker; tiered cache + request-collapsing by default). Two hard parts drive it: (1) `ctx.cache.purge()` is **entrypoint-scoped** and the zone HTTP purge is **inert** against Workers Cache, so cross-Worker invalidation (`POST /api/promote` → SSR HTML) moves to a **Cloudflare Queue** consumed by the SSR Worker — **reverses ADR 0010's mechanism** (its own deferred Option C); (2) the native key is the full **order-sensitive** query string, so AECI-100/143/223 normalization (utm-strip / per-route allowlist / canonical order) is preserved via a **gateway entrypoint** (`cache.enabled:false`) that sets `cf.cacheKey` on a `ctx.exports` loopback to a cached `Renderer` entrypoint. **Amends ADR 0004** (Cache-Tag purge retained; transport changes). Resolves the six open questions — `cross_version_cache` **left at the per-version default** initially (auto-invalidates template deploys; `true` would need a post-deploy `purgeEverything`), gateway normalization, deployed-preview-only local HIT/MISS verification, SWR/`stale-if-error` deferred, API Worker cache **stays disabled**, and a Queue (not a service-binding call) for cross-Worker purge. Per-env rollout is **prod-gated** on WC-4/5/6/8. Builds on ADR 0013 (cron→queue→consumer shape) and 0016 (D1/Drizzle topology).
- `0018-claims-attach-to-mechanism-row-agreement-computed.md` — **Accepted** (2026-06-30; AECI-288 / Stage 1.5): the two load-bearing modelling choices for the **Integration Redesign**. (1) **Claims attach to the integration (mechanism) row** — identity `(integration_id, data_object_id, direction)`; a pair connected by two mechanisms that both move RFIs is **two claims**; the product-PAIR page is a *query-time grouping*, needing **no `integrations`-table migration** (no unique pair index exists, none added). Direction is stored relative to the row's endpoints (`a_to_b`/`b_to_a`/`both`) and translated to context-relative `outbound`/`inbound`/`both` at the API. (2) **Agreement is computed-not-stored** — a pure `computeAgreement(attestations) → AgreementState` (`packages/shared/src/agreement.ts`), *vendor-vs-vendor only* with the **AECi attestation excluded from the vote** (the **AECi-never-red** rule), so an AECi-only claim can never be `conflict`; in Stage 1.5 (no vendor portal) every claim is **"Unverified"** and the `confirmed/total` headline shows `confirmed = 0`. **Amended 2026-08-14 (AECI-605):** the state set gains `single_source` and `confirmed` narrows to **two distinct vendor identities** (deduped by `attested_by_vendor_id`), so a lone vendor's affirmation is never rendered as bilateral agreement — see the amendment at the foot of the ADR and `STAGE_2_ATTESTATIONS_SPEC.md` §4. Ships `vendor_a`/`vendor_b` sources + `introduced_at`/`deprecated_at` stamps **dormant** for Stage 2 (AECI-301/303). Builds on 0016 (D1/Drizzle) and 0008 (taxonomy reference data — the `data_object` vocab mirror); the pair page reuses 0010 (promote purge) + 0011 (serving-origin canonical). Spec anchor: `docs/STAGE_1_5_SPEC.md` §3, §6.
