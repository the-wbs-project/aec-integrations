# Architecture Decision Records

Short, dated records explaining *why* specific decisions were made. Format: Context, Decision, Consequences.

See [adr.github.io](https://adr.github.io/) for the convention.

## Naming

`NNNN-short-decision-title.md` where NNNN is a four-digit sequential number starting at 0001.

- `0019-main-is-production-line-stage-2-integration-branch.md` — **Accepted** (2026-07-05): production went live, so **`main` becomes the production/stable line** and **Stage 2 develops on a long-lived `stage-2` integration branch**. A deliberate, time-boxed exception to §10's "no long-lived branches" rule (this ADR **scoped-supersedes** `docs/CICD_PLAN.md` §10 for the Stage 2 window). Rationale: the promote chain is a single linear trunk gated by SHA, so once Stage 2 lands on `main` a hotfix SHA drags in every in-progress Stage 2 commit **and** `promote-to-prod`'s forward-only `wrangler d1 migrations apply` ships any Stage 2 schema to prod on the next promote — feature flags hide UI, not migrations (ADR 0016). Keeping `main` clean makes the existing hotfix path (branch→PR→merge→promote-by-SHA) work unchanged and guarantees prod D1 never sees a Stage 2 migration until `stage-2 → main` merges. No CI/CD change (staging still auto-tracks `main`; promote buttons already take an arbitrary SHA; `drift-check.yml` is base-branch-agnostic). Costs: long-lived-branch drift + an eventual large merge (mitigated by frequent `main → stage-2` merges) and migration-journal reconciliation before merge-up. Interacts with ADR 0016 (forward-only D1 migrations — the decisive constraint), 0017 (shared auth — unaffected).

- `0021-async-promote-ingest-via-workflows.md` — **Accepted** (2026-08-12, **amended 2026-08-13**; AECI-563 + AECI-571 / epic AECI-561): the promote ingest moves off the request into a **Cloudflare Workflow**. `POST /api/promote` validates synchronously and returns `202 { jobId }`; the plan-then-batch commit runs in one **non-retried** step; `GET /api/promote/jobs/:id` serves status + the full ID map. Fixes a live-prod data-loss class: the review app's 30s abort left AECi's `db.batch` committed (product live) while the response carrying the assigned IDs was lost — and since AECi upserts only by caller-supplied `supabaseId` and stores no curation-tool key, that was **unrecoverable**, with a blind re-promote minting duplicates. **The caller-supplied job ID is the Workflow instance ID**, so `create({ id })`'s duplicate guard makes a replayed kick-off unable to commit twice — this is what replaced the **rejected** `airtable_record_id` column (AECI-562, vetoed: no curation-tool key in the public schema). Post-commit hooks stay `ctx.waitUntil` (dispatched after the step, so a replay can't re-fire them) so the job completes the instant the batch commits; oversize bundles stage in a new per-env `PROMOTE_KV` (params cap 1 MiB) and the ID map is mirrored there for 90 days, outliving the 30-day instance retention. **Hard cutover** — always `202`, no dual mode — so prod could not be promoted until the review app's AECI-567 shipped (both landed 2026-08-12/13; gate cleared). **Amendment (2026-08-13, AECI-571):** the originally-accepted **residual at-least-once window** (an engine crash between commit and step-result persistence could replay a create) is **closed**, at the cost of the ADR's original "no D1 schema change" property — the ingest now writes a `promote_jobs` ledger row keyed by the job id as the **first statement of the promote's own `db.batch`** (migration `0010_lazy_junta.sql`), so an engine replay trips the primary key, rolls the batch back, and returns the recorded IDs. The commit is exactly-once against client **and** engine death. One accepted cost remains: the error contract moved (`SLUG_CONFLICT` / `INTERNAL_ERROR` now arrive via the poll, not an HTTP status). Narrows ADR 0013's cron→queue posture for a request-triggered job; builds on 0016 (D1 has no interactive transactions) and 0010 (the purge still fires post-commit, now from the Workflow).


- `0022-cron-bookkeeping-exempt-from-audit-invariant.md` — **Accepted** (2026-08-12; AECI-573 / epic AECI-572): the `STAGE_1_SPEC.md` §26.1 audit invariant **scopes to domain state**; derived and log-class writes are exempt, and **scheduled deletion is not**. Written because the admin-panel epic's cron-written `metrics_daily` / `job_runs` tables would otherwise emit audit rows forever for records no person initiated — but the decisive finding was that **§26.1 as written was already false**: `API_CONTRACTS.md` §6.9/§6.13 had silently narrowed it to "state-changing **domain** writes" to exempt `page_views` / `mailing_list` / `feedback` (including the unsubscribe soft-delete), and that qualifier appeared in none of §26.1, `DATABASE_SCHEMA.md` §18, or `CLAUDE.md`. Six live exemptions existed, one documented. The exemption test is **three-part and conjunctive** (derived-or-log-class · invisible on public surfaces · reproducible by re-running the job) and keys on **entity class, not actor class** — a system/cron actor writing domain state still audits, which is why `POST /api/promote`'s `actorType: 'system'` writes are unaffected. Exempt today: `page_views`, `mailing_list`, `feedback`, `stats_cache` (home-stats + Algolia watermark), the denormalized product counters, and `metrics_daily` / `job_runs` once they ship; observability for these is `job_runs` + Datadog. **Any scheduled `DELETE` emits one summary `audit_log` row per run** (`retention.pruned`, with `{table, cutoff, rowsDeleted}`) in the same batch — deletion is the one write whose fact can't be recovered afterwards. Answering "yes" instead was rejected because it would force `metrics_daily` into a batch and destroy the per-key partial-failure isolation `lib/home-stats.ts` specifies. Surfaces, without legitimizing, a genuine §26.1 violation in the `*/15` reconciliation sweep (`lib/linear.ts` mutates `vendor_requests` / `workflow_instances` unaudited — **AECI-591**). Builds on 0016 (`db.batch` is the atomic unit).
- `0023-vendor-portal-live-updates-via-revalidation.md` — **Accepted** (2026-08-19; AECI-626 / epic AECI-516): the vendor portal's "live" behaviour is **scoped client revalidation over a per-vendor freshness cursor** — a new read-only `GET /api/vendor/updates` returning a **per-scope** revision map (`profile`/`entitlement`/`products`/`integrations`/`notifications`/`requests`) as **six SELECTs in one `db.batch`**, polled at **20 s focused / 60 s unfocused / paused hidden** (error backoff to a 160 s cap), with the client refetching **only** the scopes that moved. **Durable-Object WebSockets and SSE are declined** — closing the third open item of `STAGE_2_SPEC.md` §8.2 (recorded as §8.6) and correcting the §7 epic table's placeholder "Durable Objects", which was §4(5)'s assumption, never a decision. The deciding evidence is an enumeration of all six events that can change portal state: **none is sub-second**, the caller's own edit needs *zero* transport (the PATCH echo already carries post-edit state), **two of the six are produced by a daily cron** (`ATTESTATION_NOTIFY_CRON` 10:00 / `ENTITLEMENT_EXPIRY_CRON` 11:00 — a socket would deliver a 24-hour-stale event in 50 ms), and the only real deadline is the concierge entitlement toggle at ≤ ~1 min. Against that, a DO costs a binding + `migrations` block in **four** wrangler envs, a WebSocket upgrade through the SSR `/api/*` passthrough, fan-out coupling on every `/api/vendor/*` write plus two cron consumers, and a failure surface with no local emulation; SSE is strictly worse (it holds a Worker invocation open *and* polls D1 inside it). Follows ADR 0021's `GET /api/promote/jobs/:id` poll precedent. Load-bearing invariant: **every cursor query reuses the scoping predicate of the handler it is a cursor for** — a divergent cursor either goes permanently stale or leaks the existence of another vendor's row. Explicitly **a dated decision with a re-open trigger**, not a permanent no: adopt DO sockets when the detectors move to write-triggered evaluation, when multi-seat concurrency produces a measured lost-update rate, or when measured `aeci.api.vendor.updates` volume exceeds a hibernating DO's cost. Build contract: `docs/STAGE_2_REALTIME_SPEC.md`. Builds on 0016 (the one-batch cursor read); no cache or WAF surface (`/api/vendor/*` is `private, no-store`, and both Pro rate-limit slots are POST-only).
