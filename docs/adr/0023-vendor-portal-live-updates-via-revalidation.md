# ADR 0023: Vendor-portal live updates ride scoped client revalidation, not Durable-Object WebSockets

**Status:** Accepted
**Date:** 2026-08-19
**Context owner:** chrisw@thewbsproject.com
**Relates to:** AECI-516 (the Real-Time / Live Portal epic) and AECI-626 (this record); closes the third open item of `docs/STAGE_2_SPEC.md` §8.2, recorded there as §8.6. Build contract: `docs/STAGE_2_REALTIME_SPEC.md`. Follows the polling precedent set by ADR 0021 (`GET /api/promote/jobs/:id`); narrows ADR 0013's cron→queue posture not at all (no queue is involved). Builds on ADR 0016 (D1/Drizzle — the cursor is six SELECTs in one `db.batch`).

> **This is a dated decision with a named re-open trigger, not a permanent "no" to sockets.** The three conditions that flip it are enumerated under [Re-open trigger](#re-open-trigger) and each is *measurable* — two of them off metrics this epic ships. Nothing below argues that WebSockets are the wrong technology; it argues that at the latency need the portal actually has, they buy nothing and cost a binding, a migration block in four environments, and a new failure surface with no local emulation story.

---

## Context

`STAGE_2_SPEC.md` §2.3 inherited §18's sentence — *"WebSockets/SSE for the portal"* — and §4(5) translated it to *"on Cloudflare Workers that means Durable Objects"*. Neither was a decision; §8.2 explicitly deferred the transport choice to this epic, and the §7 epic table has carried the word "Durable Objects" as a placeholder ever since. Three downstream build specs then wrote "transport still open" into their own out-of-scope lists (`STAGE_2_VENDOR_PORTAL_SPEC.md` §11, `STAGE_2_ATTESTATIONS_SPEC.md` §1.3(4) / §7.2 / §11, `STAGE_1_5_SPEC.md` §10), so the open question had propagated to five documents without anyone having established what latency the portal needs.

So the first thing this epic did was enumerate every event that can change a vendor's portal state, and how fast each must land:

| Event | Producer | Real latency need |
|---|---|---|
| The vendor's own edit (profile / product / attestation / claim) | the caller's own request | **zero transport** — the PATCH/PUT echo already carries post-edit state |
| Detector nudge (`silent-counterparty`, `open-conflict`, `stale-version`, `aeci-denied`) | `ATTESTATION_NOTIFY_CRON = '0 10 * * *'` — **once a day** | ≤ minutes; email is the primary channel |
| Term-expiry warning | `ENTITLEMENT_EXPIRY_CRON = '0 11 * * *'` — **once a day** | ≤ minutes; email is primary |
| Entitlement set/renew/clear (the concierge toggle) | a human admin, `PATCH /api/admin/vendors/:id/entitlement` | ≤ ~1 min — this is the *only* concrete latency need on the surface |
| Counterparty attests / retracts | another vendor, human-paced | ≤ minutes |
| Claim approved → seat granted | a human admin | the vendor has no portal until it lands |

**Nothing on that list is sub-second.** Two of the six are generated by a **daily cron** (`apps/api/src/scheduled.ts` — the 10:00 and 11:00 UTC slots), so a persistent socket would deliver a 24-hour-stale event with 50 ms of transport latency. The single event with a real deadline — the concierge entitlement toggle, where an admin is often on the phone with the vendor — needs "about a minute", not "about a frame".

The other half of the context is what a socket costs *here*, in this repo, today:

- **A `durable_objects` binding plus a `migrations` block in four wrangler environments** (`preview`, `staging`, `demo`, `production`) on `apps/api/wrangler.jsonc`. DO migrations are the one Cloudflare config class that is not additive-safe by inspection.
- **A WebSocket upgrade threaded through the SSR Worker's `/api/*` service-binding passthrough.** The browser never talks to the API Worker directly; every `/api/*` call is proxied. An upgrade is not a request the proxy handles today.
- **Fan-out coupling on every write.** Each `/api/vendor/*` write, the admin entitlement action, and two cron consumers would have to locate and notify the right DO. That is a new obligation on code paths whose current invariant list (the §26.1 audit row in the same `db.batch`, the purge enqueue, the metric) is already the thing reviewers check.
- **A new failure and observability surface with no local emulation story.** Wrangler does not reproduce the deployed socket lifecycle, which is the same gap ADR 0020 §Q3 recorded for native Workers Cache — and there the answer was "verify on a deployed preview", which is expensive per-change.

**SSE without a DO is strictly worse than either option.** It holds a Worker invocation open for the life of the stream and still has to poll D1 from inside it — paying the polling cost *and* the long-lived-invocation cost, to deliver events that arrive once a day.

Finally, the repo already has a house pattern for *"the server did something, tell the client"*: ADR 0021's `GET /api/promote/jobs/:id` kick-off/poll/collect protocol. And `STAGE_2_SPEC.md` §8.1's **concierge onboarding model** caps launch concurrency at roughly one actively-editing seat per vendor — which is also what makes multi-seat conflict resolution a non-problem today.

## Decision

**Vendor-portal live updates are delivered by scoped client revalidation over a cheap per-vendor freshness cursor. Durable-Object WebSockets and SSE are not adopted.**

- **A new read-only endpoint, `GET /api/vendor/updates`**, behind `requireVendor()` (`apps/api/src/lib/authz.ts:422`) and scoped to `c.get('auth').vendorId` — **no vendor id crosses the wire**, per the AECI-520 scoping invariant. It returns a **per-scope** revision map (`profile` · `entitlement` · `products` · `integrations` · `notifications` · `requests`) plus `server_time`, computed as **six SELECTs in one `db.batch([...])`** — one D1 round trip. It is a pure read, so it writes **no `audit_log` row**; §26.1 governs writes, and adding one here would be wrong.
- **Per-scope, not one opaque revision.** The client then refetches **only** what moved: `profile`/`entitlement`/`products`/`requests` → `GET /api/vendor/me` (one deduped call), `integrations` → `GET /api/vendor/integrations`, `notifications` → `GET /api/vendor/notifications`. An opaque single revision would turn every counterparty attestation into a full-dashboard refetch.
- **Every cursor query reuses the scoping predicate of the handler it is a cursor for.** This is the load-bearing invariant of the design: a cursor that scopes differently from its payload either goes permanently stale (it never moves when the payload does) or leaks the existence of another vendor's row (it moves when the payload cannot). The sources are pinned to the shipped handlers — the ownership set in `createListVendorIntegrationsHandler` (`apps/api/src/routes/vendor-attestations.ts:679-691`), the exact notification predicate at `routes/vendor-notifications.ts:132-140`, and the request predicate at `routes/vendor.ts:455-465`.
- **A visibility-aware poll loop** (`VendorLiveSync`): **20 s** visible-and-focused · **60 s** visible-unfocused · **paused with no timer** when hidden; immediate poll on `visibilitychange`→visible and on `online`; error backoff 20 → 40 → 80 → **160 s cap**, reset on success. Browser-only — started from `afterNextRender`, torn down via `DestroyRef`, never during SSR. *(As built 2026-08-19, two refinements that do not change the decision: the `online` poll is **gated on visibility** — a flapping connection would otherwise wake a hidden tab repeatedly and reintroduce the overnight cost the pause removes — and the backoff is **floored at the current cadence** (`Math.max(base, backoff)`), because the first step (20 s) is shorter than the unfocused interval (60 s) and a bare ladder would answer an outage with three times the healthy load. `STAGE_2_REALTIME_SPEC.md` §4.1 / §4.5.)*
- **A shared `VendorPortalStore`** owns the portal payload so a write in one section moves the counts in another, and so the sync loop has one place to reconcile into. **Toggle-shaped writes** (assert / deny / retract) apply optimistically and roll back visibly on failure; **form-shaped writes** (profile, product) deliberately keep their pessimistic echo-reconcile.
- **A write in flight is never clobbered.** If a section holds unsaved local changes, reconciliation for that section defers and a non-blocking "Updated elsewhere — reload this section" affordance appears. Silently replacing a half-typed form is worse than being stale.
- **`aeci.api.vendor.updates`** (count), tagged `changed` ∈ `none | some`, is the metric that makes this decision reviewable rather than permanent: a high `none` ratio is evidence to lengthen the interval, a high `some` ratio is evidence for the DO.

**This decision is not "no live updates".** Both §2.3 scope bullets ship: a vendor's edit reflects without a full reload, and new detector nudges appear in-portal within one poll interval. What does not ship is a **persistent socket**. Email stays the primary channel for the two cron-generated event classes, exactly as `STAGE_2_ATTESTATIONS_SPEC.md` §7.2 specifies.

**No WAF exposure.** The blanket `/api/*` rate-limit rule was removed when both Pro-plan slots were spent on the two write endpoints (`docs/waf-rate-limits.md` §"2-slot trade-off"); both remaining rules are POST-only. A 20-second authenticated GET trips nothing.

**No cache exposure.** `/vendor` and `/api/vendor/*` are private and never edge-cached — `json()` stamps `Cache-Control: private, no-store` (`apps/api/src/http.ts:17`). Nothing in this epic emits a `Cache-Tag` or enqueues a purge, and the store must not be imported by any cacheable SSR component.

## Consequences

**Gained**

- **Zero new infrastructure.** No binding, no `migrations` block, no queue, no provisioning step in any deploy workflow, and nothing new to add to the four wrangler environments. The whole transport is one Hono route plus two browser-side classes.
- **It works identically in `wrangler dev`.** Unlike a socket (and unlike the native cache — ADR 0020 §Q3), the entire mechanism is exercisable locally and in unit tests with fake timers. There is no "only verifiable on a deployed preview" class of behaviour introduced here.
- **The write paths are untouched.** No `/api/vendor/*` handler, no admin entitlement action, and neither cron consumer learns anything about notification fan-out. Their invariant lists stay as they are.
- **One D1 round trip per poll**, not one per section, because the cursor is a single `db.batch`. The refetch that follows only fires for scopes that actually moved.
- **Consistency with the house pattern.** A reviewer who understands `GET /api/promote/jobs/:id` understands this without new concepts.

**Accepted costs**

- **Up to one poll interval of staleness** (≤20 s focused, ≤60 s unfocused, unbounded while the tab is hidden — resolved by the immediate poll on `visibilitychange`). For the one event with a real deadline, the concierge entitlement toggle, 20 s clears the "≤ ~1 min" bar with room; for the rest it is far inside the need.
- **A steady request floor per open portal tab.** Three requests a minute per focused seat, against a concierge cohort. This is the cost the `aeci.api.vendor.updates` counter exists to measure, and it is the third re-open condition below.
- **A cursor invariant that a future endpoint can break silently.** Adding a `/api/vendor/*` list endpoint without adding (or correctly scoping) its cursor row produces a section that never live-updates, with no error anywhere. `STAGE_2_REALTIME_SPEC.md` §2 states the invariant and `docs/AUTH_AND_RLS.md` carries the per-endpoint row that makes the omission visible in review.
- **Optimistic toggles introduce a rollback path that must be visible.** A failed assert that silently reverts looks like a UI glitch; it has to name the failure. This is real UI surface area that a pessimistic design would not have.
- **The word "Durable Objects" in `STAGE_2_SPEC.md` §7's epic table was wrong for the life of the outline** and is corrected by this ADR's companion sweep. Anyone who planned against that row planned against a placeholder.

## Alternatives not taken

- **Durable-Object WebSockets (with hibernation).** The technically strongest option and the one §4(5) assumed. Rejected **for now, on cost-vs-need**, not on capability: every event it would deliver sub-second is produced either by the caller's own request (already echoed) or by a once-a-day cron. The costs are enumerated in Context; the trigger that reverses this is below.
- **SSE from the API Worker.** Rejected outright, and unlike the DO it has no re-open trigger: it holds a Worker invocation open *and* polls D1 inside it, so it is a strict superset of this decision's cost with none of a DO's push semantics.
- **One opaque revision token for the whole portal.** Simpler endpoint, but any counterparty attestation or admin toggle would force a full refetch of `me` + `integrations` + `notifications` — three calls where the per-scope map needs one, on the interval, forever.
- **Polling the existing endpoints directly** (re-`GET /api/vendor/me` every 20 s and diff client-side). No new endpoint at all, but it moves the entire payload every interval instead of a six-field cursor, and it cannot tell "nothing changed" from "changed back", which is what makes the `changed:none` ratio measurable.
- **Server-driven push over the existing cache-purge Queue** (ADR 0020's transport). The queue reaches the SSR Worker's cache, not a browser. There is no consumer that could hold a client connection without introducing exactly the DO this ADR declines.

## Re-open trigger

Adopt Durable-Object WebSockets when **any one** of the following holds. Each is a measurable condition, not a judgement call:

1. **The detectors move off the daily cron to write-triggered (sub-minute) evaluation.** The moment `ATTESTATION_NOTIFY_CRON`'s work happens on the write that causes it, the "24-hour-stale event delivered in 50 ms" argument evaporates and push starts to mean something.
2. **Multi-seat concurrent editing produces a measured lost-update / stale-overwrite rate.** Today §8.1's concierge model caps launch concurrency at roughly one actively-editing seat per vendor. If that stops being true, the deferred-reconciliation affordance (§5 of the build spec) stops being sufficient and coordination becomes the real requirement — which is what a DO is actually for.
3. **Measured `aeci.api.vendor.updates` request volume at the shipped cadence exceeds the cost of a hibernating DO.** This is the one condition that arrives on its own: the metric ships with the epic, and the `changed` tag distinguishes "we are polling too often" (lengthen the interval first) from "there is genuinely this much to deliver" (adopt the socket).

If any trigger fires, this ADR is superseded rather than amended — the endpoint, store, and sync loop all survive a socket adoption as the fallback path for a client whose connection is down, so the successor is additive.
